twing — making a design readable
What has to change, and why · 2026-09-14 · implemented on feat/structured-design-rendering (twing-cli) and feat/render-structured-designs (twing-monitor)
The question
Do both twing-CLI and twing-monitor need to change?
The answer
Yes — both. The CLI has to start recording information it never captured. The monitor has to start showing information it never received.

Neither one alone fixes anything. The monitor cannot display a distinction the CLI never wrote down, and the CLI recording richer data changes nothing if the monitor keeps rendering the old fields.

What's wrong today

A design records where work will happen. It has never recorded what will happen there.

Today

A paragraph of prose, plus three bags of strings:

creates: ["RetryPolicy"]
touches: ["src/net/retry.ts", "drizzle/0014.sql", ".twing/twing.yml"]

A source file, a database migration and a config file sit in one list, indistinguishable. Renaming something and rewriting it look identical. The card shows you "3 created, 7 touched".

Needed
modifyRetryPolicy.backoff
exponential growth, capped at 30s
addRetryPolicy.jitter
full jitter so retries desynchronise
renameRetryPolicy.reset ← clear
name matches the other lifecycle methods

A verb, a target, and a reason. Now it can be grouped into Code / Schema / API sections, and a manager can read it.

Why each side changes

twing-CLI

Produces & stores the record
  • Capture a verbToday a design says a file is involved. It must say whether that file is being added, modified, rewritten, removed or renamed — those are different claims.
  • Capture a kindIt must record that something is a migration rather than a source file. This is the only reason "schema changes" can ever become a section.
  • Persist and serve itThe structured record needs a column and an API field, or the monitor has nothing to fetch.

twing-monitor

Presents the record
  • Render the new shapeToday it reads only the old string bags and draws them as chips. It would ignore the structured data entirely — new rendering code is required.
  • Group into sectionsCode, Schema, API, Tests — the fixed layout a manager learns once, with a one-line blast-radius summary at the top.
  • Compare declared vs actualThe monitor already fetches what a session really edited. Showing it beside what was declared is nearly free, and it is the most valuable thing on the card.
The split in one sentence. The CLI decides what is worth knowing about a design; the monitor decides how a human reads it. The first is a data problem, the second is a presentation problem, and they have to be solved in that order.

Caveat worth knowing. The structured format is used when someone authors a design deliberately. Most designs today are registered automatically at the end of plan mode, and those still produce the old shape. So the improved card will be the exception until plan mode emits a structured design too — a decision worth making early, because it determines whether this is the normal view or a rare one.

Nothing here risks the edit gate. The old fields keep being filled in automatically from the new ones, so the part of twing that actually blocks work carries on reading exactly what it reads today. Designs that predate the change keep rendering the way they do now.
