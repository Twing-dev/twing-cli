01 What v1 is

Today a design says where:

touches: ["src/net/retry.ts", "drizzle/0014.sql", ".twing/twing.yml"]

v1 makes it say what — three fields per item, nothing more:

changes:
  - id: c1
    action: modify
    target: src/net/retry.ts::RetryPolicy.backoff
    intent: "exponential growth, capped at 30s"

The whole trick target uses the same path::Symbol.method format twing already records real edits in. So “did you build what you said” becomes a set comparison, not a model call.

In v1

action · target · intent · id, plus from for rename/move. Six actions. That's it.

Deliberately not in v1

kind, verification[], contracts, decisions, reads — and no review checks yet. Each arrives when something actually reads it.

Why hook/ must stay untouched The hook is the one artifact whose version is exact-matched by the gate. Touching it means a Go release, a new 426 surface, and the worst version-skew axis in the system — for a change that needs none of it. It already sends only rawPlanText on the common path and reads back only touches. Keep returning touches and it never notices anything happened.

If the implementation ever needs hook/ edited — stop and redesign.

03 The code

packages/core/src/types.ts — the shape 
/** One declared change inside a design (2026-09, structured design template).
 *
 * `target` deliberately uses the SAME `path::Symbol.method` format
 * `Claim.symbolId` uses -- that shared namespace is what turns
 * design-vs-code conformance into a set difference instead of an LLM
 * judgement. Do not introduce a second spelling here. */
export interface DesignChange {
  /** Stable within this design. Findings point at it. */
  id: string;
  /** Splits on one question: is behaviour supposed to change?
   *  add/modify/rewrite/remove  -> yes, prove the stated change happened
   *  rename/move                -> no,  prove the body is identical */
  action: "add" | "modify" | "rewrite" | "remove" | "rename" | "move";
  /** `src/net/retry.ts` or `src/net/retry.ts::RetryPolicy.backoff`. */
  target: string;
  /** One sentence: what this achieves, not what it does mechanically. */
  intent: string;
  /** The previous name (rename) or path (move). Absent otherwise. */
  from?: string;
}

And on DesignStatement, one optional field:

  /** Structured declaration, when the design was registered with one.
   * Optional and never backfilled: every design row created before this
   * shipped has none, and readers must treat absence as "not stated"
   * rather than "no changes". `creates`/`touches` stay authoritative for
   * the gate and are derived from this when it is present. */
  changes?: DesignChange[];
packages/core/src/design-scope.ts — the derivation NEW

The single place creates/touches are computed, so the CLI and the server cannot drift:

import type { DesignChange } from "./types.js";

/** `src/net/retry.ts::RetryPolicy.backoff` -> `src/net/retry.ts` */
function pathOf(target: string): string {
  const i = target.indexOf("::");
  return i === -1 ? target : target.slice(0, i);
}

/** Derives the legacy scope fields from a structured declaration.
 *
 * Exists so `creates`/`touches` keep working untouched for every existing
 * reader -- `pathInDesignScope` (the Edit/Write gate), `hook/design_gate.go`
 * and twing-monitor all still read them and need no changes. Deduped,
 * because several changes routinely target one file. */
export function deriveScope(changes: DesignChange[]): { creates: string[]; touches: string[] } {
  const creates = new Set<string>();
  const touches = new Set<string>();
  for (const c of changes) {
    (c.action === "add" ? creates : touches).add(pathOf(c.target));
  }
  return { creates: [...creates], touches: [...touches] };
}
db/schema.ts + migration 0016 — storage

One column, following the table's existing JSON-as-text convention:

    /** Structured design declaration (2026-09). JSON DesignChange[],
     * defaults to "[]" for pre-existing rows via the migration -- never
     * backfilled, same convention as justifiedOverlaps and friends. */
    changes: text("changes").notNull().default("[]"),

Generated migration:

-- 0016_design_changes.sql
ALTER TABLE `designs` ADD `changes` text DEFAULT '[]' NOT NULL;

Runs automatically — createDb() calls migrate() on startup. No operator action on deploy.

app.ts — accepting it, without breaking old clients

On DesignCheckRequestBody:

  /** Structured declaration (2026-09). When present, `creates`/`touches`
   * are DERIVED from it and any client-supplied values are ignored -- one
   * source of truth. When absent, the old flat fields are used exactly as
   * before, which is what keeps pre-0.2.26 clients working. */
  changes?: DesignChange[];

And in the handler, before registration:

let changes = body.changes;
if (changes && changes.length > 0) {
  const derived = deriveScope(changes);
  creates = derived.creates;
  touches = derived.touches;
}

Additive, in both directions An old client sends no changes → behaves exactly as today. A new client against an old server → the field is ignored, and the derived creates/touches it also sends keep everything working. Neither combination breaks.

design-extract.ts — and the hallucination guard

The prompt produces changes[] instead of two string arrays. The important part is what happens after:

/** Drops any extracted change whose target doesn't exist in the repo and
 * isn't declared as `action: "add"`.
 *
 * A model asked for ten structured fields hallucinates more than one asked
 * for four string arrays. This is the mitigation, and it is one twing can
 * do that a diff-only tool cannot: the repository is right there, and
 * Tree-sitter is already a dependency. Silently dropping is deliberate --
 * an invented target that reaches the store becomes a permanent false
 * "declared, never built" finding for the reviewer. */
function dropUnresolvableTargets(changes: DesignChange[], repoRoot: string): DesignChange[]

Acceptance bar, matching the precedent the semantic comparator set with its 25-case labelled eval: zero hallucinated targets, measured against real plan text from this repo's own design history.

cli/src/design.ts — --from <file> 
twing design register --from design.yml

Four steps, in order:

  1. Parse the YAML (the yaml package is already a @twing/core dependency — no new package)
  2. Validate — every id unique, every action one of the six, from present iff rename/move
  3. Check targets against the repo — warn, never block, mirroring the existing warnIfTouchesMissing
  4. Derive and send changes and creates/touches, so an old server still works

The existing flag form (--summary, --touches) stays exactly as it is. --from is an alternative, not a replacement.

04 What it looks like

The file a developer writes

# design.yml
goal: "Outbound HTTP survives transient failures without thundering herd"

changes:
  - id: c1
    action: modify
    target: src/net/retry.ts::RetryPolicy.backoff
    intent: "exponential growth, capped at 30s"

  - id: c2
    action: add
    target: src/net/retry.ts::RetryPolicy.jitter
    intent: "full jitter so retries desynchronise"

  - id: c3
    action: rename
    target: src/net/retry.ts::RetryPolicy.reset
    from: RetryPolicy.clear
    intent: "name matches the other lifecycle methods"

Registering it — the happy path

$ twing design register --from design.yml reading design.yml ✓ 3 changes, 3 targets resolve in this repo derived creates = src/net/retry.ts touches = src/net/retry.ts verdict: clean design: a1b2c3d4-e5f6-4789-abcd-0123456789ab group: a1b2c3d4-e5f6-4789-abcd-0123456789ab declared c1 modify RetryPolicy.backoff c2 add RetryPolicy.jitter c3 rename RetryPolicy.reset (from RetryPolicy.clear)

A typo — caught before it reaches the coordinator

$ twing design register --from design.yml reading design.yml ✗ c2 target does not exist in this repo src/net/retry.ts::RetryPolicy.jiter no `action: add` declares it — typo, or did you mean `add`? ! registering 2 of 3 changes. Fix design.yml and re-run to add c2. verdict: clean design: a1b2c3d4-e5f6-4789-abcd-0123456789ab

Warns and proceeds rather than refusing outright — same call warnIfTouchesMissing already makes. A path that's merely relative to a subdirectory shouldn't block a registration a human clearly meant.

An invalid action — this one does refuse

$ twing design register --from design.yml ✗ c3 unknown action "refactor" valid: add · modify · rewrite · remove · rename · move closest: rewrite (behaviour may change) or rename/move (it must not) nothing registered.

05 Shipping it

Release A
Server only · 0.2.26

Core types, migration 0016, store, app.ts accepts changes. Extraction unchanged.

Nothing sends the new shape yet. A no-op release that makes the server tolerant.

Release B
Clients · 0.2.27

Extraction produces changes[]; --from lands in the CLI.

By now every deployed server already understands it.

Why two releases and not one The gate exact-matches hook ↔ server, but there is no check at all between CLI and server. During any rollout you will have old CLIs talking to a new server. Splitting this way means there is never a moment where a client sends something the deployed server rejects.

Both are patch bumps — additive, no manifest change, no operator action, migration runs itself.

git checkout -b feat/structured-design-changes     # from main
# …build, test locally against production…
git push -u origin feat/structured-design-changes  # PR → review → merge

git checkout main && git pull
# bump core + cli + server package.json → 0.2.26  (one commit)
git tag v0.2.26 && git push origin v0.2.26

# ⏸  WAIT for release-npm.yml to go GREEN
cd deploy/docker && docker compose build && docker compose up -d

The one thing that must not be rushed Deploy the coordinator before npm has published and every client 426s — and the deny tells them to install a version that isn't there yet. Dead end for everyone until npm catches up. Tag → green → deploy. Never the same breath.

Nobody has to upgrade by hand Since 0.2.23 the daemon watches the coordinator's declared version and installs that exact version itself — CLI, hook binary and a daemon restart. Deploying the coordinator is what moves everyone.

06 Before writing any of it

The cheapest possible check that the template is worth building, from a throwaway repo, with zero code changed:

  1. write design.yml in the new template
  2. send its text as the plan — the server stores it verbatim and fills the file lists by extraction
  3. open twing-monitor — read the template as a human would

If it doesn't read well there, no amount of implementation fixes it — and you've spent ten minutes instead of a week.
