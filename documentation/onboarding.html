01 Four stances worth more than any library

These are the real prerequisites. Internalise them or you will fight the code — every one of them looks like an inconsistency until you see why it isn’t.

Stance 01
Fail-open vs. fail-closed is a per-path decision

Not a global policy. Capture fails silently; the gate denies. Same binary, opposite defaults, deliberately. Ask “which path am I on?” before choosing an error behaviour.

Stance 02
Ground truth beats self-report — and both exist on purpose

A design’s touches is what someone claimed; a Claim is what Tree-sitter saw. Whenever two checks look redundant, that’s usually why: /v1/constraints/match exists precisely because the self-reported version was bypassable.

Stance 03
Append-only, never backfill

New column → old rows keep reading correctly without it, and readers handle its absence. This is not laziness; it’s what makes three independently-updated deployables survivable.

Stance 04
A deny message is a product surface

Not an error string. Three-layer grammar, no colour, no emoji, exact commands. Collapsing 401 and 403 into one message cost a real user five days. Treat that text as code.

02 Vocabulary you must own first

These are invented terms with precise local meanings, and every file assumes you already have them. They’re defined in packages/core/src/types.ts.

TermMeans
ClaimA record that a session touched a specific symbol. Derived from the AST, not declared. Path 1.
FindingThe output of a divergence check over claims — structured, so align can say who and why.
DesignStatementA session’s declared plan: summary + creates/touches/dependsOn. Path 2.
VerdictOne of the four buckets. Determines whether an edit blocks and who can approve the override.
ConstraintA project rule: a statement plus path globs. Always blocks; only an admin waives it.
Alignment threadThe async, voluntary conversation between two developers a finding names.
scope-matchThe gate’s own question: is this literal file inside this session’s declared scope?
DivergenceAny of the ways two parties’ work is discovered to be in tension.

03 Prerequisites checklist

Ordered by how much leverage each gives you here, not by general importance. Tick items off — progress is saved locally in this browser.

1 · Claude Code hooks must

The highest-leverage item by a wide margin — the entire system is one application of the hooks API, and none of the code parses without it. Learn the event names (PreToolUse, PostToolUse, SessionStart, UserPromptSubmit, SessionEnd), the JSON payload on stdin, hookSpecificOutput with permissionDecision and permissionDecisionReason, additionalContext, matcher syntax, and how hooks from different settings scopes merge and all fire. Read hook/main.go and wire-hooks.ts alongside the docs.

2 · TypeScript on Node 20+, ESM, project references must

Not advanced types. You need "type": "module" and .js extensions in relative imports (yes, even from .ts), tsc -b composite builds across workspaces, and node --test. Tests run against dist/, not src/ — build first. That trips up everyone exactly once.

3 · Enough Go to read one small module must

hook/ is ~1 700 lines of plain Go. Structs with JSON tags, net/net/http, encoding/json, os/exec, error-as-value handling, go test ./.... You do not need goroutines, channels, or generics — the hook deliberately has none.

4 · Git plumbing as an API must

The codebase shells out to git constantly: rev-parse --show-toplevel, remote get-url origin, merge-base, diff --name-status, show <rev>:<path>, symbolic-ref refs/remotes/origin/HEAD. Also understand worktrees vs. clones, and why both produce the same projectId.

5 · Version skew across independent deployables must

Three artifacts update on different schedules: @twing/cli (npm), twing-hook (a GitHub release fetched only by twing init), and the deployed coordinator. Four mechanisms exist just to manage that. Skew is the normal state, not an edge case — see Findings.

6 · Concurrency & idempotency intuition must

This is a distributed system with eventual consistency, and the races are handled explicitly rather than avoided. Learn to spot the pattern: scopeVersion for cooperative cancellation, re-fetching live state after a slow await, onConflictDoNothing for racing first contact, clearing a batch before awaiting, capturing a timestamp before a request rather than after. If TOCTOU isn’t already a reflex, build it.

7 · The §-numbering convention must

Source comments cite §4, §17, §17.9 constantly and assume you can look them up. Skim docs/orchestrator-and-verification-design-doc_v1.md far enough to know what §4, §5, §6, §8, §11, §12 and §17 cover.

8 · Tree-sitter / AST basics should

Concrete syntax trees, named nodes, node types (function_declaration, method_definition, variable_declarator), childForFieldName, walking ancestors. Enough to follow symbol-id.ts — specifically why a structure-derived id survives line drift when a line-number one wouldn’t.

9 · Unix sockets & message framing should

Why a stream socket needs length-prefixed frames at all (writes coalesce and split), and how a streaming decoder buffers partial frames. framing.ts is 45 lines and is the whole lesson.

10 · Hono should

A small web framework. Mainly: middleware runs in source registration order (auth, CORS and the version check are ordered deliberately), and route matching is registration-ordered too — which is why /v1/designs/:id must come after /v1/designs/scope-match.

11 · Drizzle ORM + SQLite should

The query-builder style (select().from().where(and(…)), .get() vs .all() vs .run()), migrations committed under drizzle/, and better-sqlite3’s synchronous API. Note the portability discipline in db/schema.ts.

12 · Glob matching with minimatch should

Constraint scopes and design touches are globs. Know the difference between packages/** and packages/*, and what each one will and won’t catch.

13 · OAuth 2.0 device flow nice

The mechanism gh auth login uses — why a CLI uses it instead of a local redirect server, and the polling contract (authorization_pending, slow_down).

14 · LLM API integration patterns nice

The OpenAI chat-completions shape (all four providers here speak it), few-shot prompting via real conversation turns, and — most importantly — the fail-soft discipline: a malformed or unreachable model degrades to “no check ran,” never to “deny everyone.”

15 · launchd and systemd --user units nice

Only if you touch daemon-service.ts. The interesting part is why the code trusts a socket probe over launchctl print’s own bookkeeping.

16 · Threat-modelling habits nice

The identity work (§17.10) reads well as a case study: hashed tokens never stored in plaintext, timingSafeEqual used for exactly the one single-secret comparison that needs it, server-side-resolved identity, and permissions verified against GitHub rather than trusted from the client.

04 What is not a prerequisite

Explicit permission to skip things, so the list above doesn’t read as a wall.

Deep Go

No goroutines, channels, or generics anywhere in hook/. If you can read a struct and an if err != nil, you’re fine.

The design doc, front to back

It’s ~65 k lines. Skim for the § numbers and treat it as a reference, not a reading assignment.

The LLM prompt engineering

design-semantic-check.ts’s prompt was tuned against a 25-case eval. Don’t touch it casually — but you don’t need to understand it to work anywhere else.

Drizzle / SQLite, on day one

Not until you touch the server. That’s days away.

Tree-sitter internals

You need the concept — structure-derived ids survive line drift. The wrapper itself is ~90 lines.

The dashboard

twing-monitor is a separate repo. Nothing here depends on understanding it.

05 Day-one gotchas in this repo

ThingWhat happens
This repo dogfoods its own gateYour first edit will be denied for having no registered design. That is the system working, not a broken setup.
The coordinator is live and sharedEvery design you register while learning is a real record under your identity, visible to teammates. Use a local twing serve for experiments.
Build before testTests run against dist/. Editing src/ and running tests tests the old code.
TWING_DESIGN_GATE=offExists for spelunking, not for shipping. Use it while reading, not while contributing.
~/.twing/design-coordinator.logEvery gate decision, with reasons. First place to look when something denies unexpectedly.
The daemon is machine-wideOne process serves every repo. “Restart the daemon” affects all your projects, not just this one.
Hooks are wired globallyRunning twing init anywhere wires ~/.claude/settings.json for every repo on the machine.

06 A first-week ramp

Reading alone won’t do it. Alternate reading with running.

0 / 0 · 0% reset
Day 1 · Read the spine

types.ts → hook/main.go → protocol.ts. About 45 minutes. Don’t chase every reference; get the shape.

Day 1 · Stand up a local coordinator

npm run start --workspace packages/server, then twing admin bootstrap against it. Now your experiments cost nobody anything.

Day 2 · Run the simulator

node simulator/dist/index.js --enable-design-gate. Two real claude sessions against a shared fixture, colliding for real. Nothing in the docs teaches as fast as watching this.

Day 2 · Break things on purpose

Delete your cached token and try to edit — watch it fail closed. Register a design, then edit an undeclared file — watch out_of_scope. Add a constraint matching a file you’re about to touch — watch the §17.9 backstop fire.

Day 3 · Read the gate end to end

hook/design_gate.go, all 1 700 lines. After days 1–2 it reads as obvious rather than dense — you’ll already have seen most of it happen.

Day 3 · Then the server

checks.ts (simplest detector) → design-checks.ts (verdict logic, all pure) → app.ts (the routes, once you know the pieces).

Day 4 · Write a test as your first contribution

The overlap-before-constraint ordering gap in Findings is a good one: small, real, and it forces you through design-checks.ts and the test harness at once.

Day 5 · Ship something small through the real gate

Use plan mode so ExitPlanMode registers the design for you. Feel the full loop from the inside — that’s the part no document conveys.

07 Reading order

  1. documentation/index.html — you are here
  2. packages/core/src/types.ts — the vocabulary. Read DesignVerdict’s doc comment twice; it is the model
  3. hook/main.go — the entry point, ~130 lines
  4. packages/core/src/protocol.ts — what the hook says to the daemon
  5. packages/cli/src/daemon/claims.ts — how an edit becomes a Claim
  6. packages/server/src/checks.ts — the simplest detector
  7. packages/server/src/design-checks.ts — the synchronous verdict logic
  8. hook/design_gate.go — the blocking path, end to end
  9. packages/server/src/app.ts — the routes, once you know the pieces

Read the comments before changing the code they sit on This codebase’s comments are unusually dense and unusually specific — most cite a date, a live incident, and what was tried and rejected. Several are the only record of why an obvious-looking simplification is wrong. Follow the convention when you add code: say what it does, and say what would break if someone “simplified” it.
