What I changed, and what the design looks like

One new flag. Below: exactly what code changed, then a real design describing this very change, and what it renders as in twing-monitor.

In one sentence You can now register a design from a small YAML file instead of typing flags — twing design register --from design.yml — and creates/touches are computed for you instead of hand-typed.

The six actions

Closed set. They split on one question — is behaviour supposed to change?

ActionMeansA checker can assert
adddidn't exist, now doesnew behaviour matches intent
modifychanged incrementallythe delta matches intent
rewritesubstantially replacedthe whole symbol matches intent
removegonenothing still references it
renamesame code, new namebody identical — pure AST check
movesame code, new placebody identical — pure AST check

Running it

twing design register --from design.yml
✓ 5 change(s) declared derived creates = packages/core/src/design-scope.ts, packages/core/src/design-scope.test.ts touches = packages/core/src/types.ts, packages/cli/src/design.ts, packages/core/src/index.ts verdict: clean design: aaa193b0-0443-4c89-b992-26359ae7eb04 declared c1 add packages/core/src/design-scope.ts c2 add packages/core/src/design-scope.test.ts c3 modify packages/core/src/types.ts::DesignStatement c4 modify packages/cli/src/design.ts::runDesignRegister c5 modify packages/core/src/index.ts

You never typed creates or touches They were computed. The two add items became creates; the three modify items became touches. If two items had named the same file, it would appear once — deduped.

Pass the right session id The gate looks designs up by Claude Code's real session id. Inside a Claude Code session, omit --session entirely and it picks up CLAUDE_CODE_SESSION_ID automatically. Pass an invented one and the design registers fine but the gate will never find it — the edit still gets denied.

06 When it refuses

Change one action to something invalid and re-run:

twing design register: design.yml isn't a valid design template. ✗ missing `goal:` -- one sentence describing what this achieves ✗ c3 unknown action "refactor" -- valid: add · modify · rewrite · remove · rename · move ✗ c3 duplicate id "c3" -- ids must be unique within a design ✗ c4 `from:` only applies to rename/move, not `modify` Nothing was registered.

All problems listed at once, and no network call is made — it fails before it ever reaches the coordinator. A target that doesn't exist on disk only warns, because that's usually a path written relative to a subdirectory rather than a mistake.

07 Known gap

Someone else has a spec for this A closed design by mbhattacharyarules@gmail.com targets docs/design-format.md and names sections this implementation has no answer for — notably "approval-reset identity" (when a design item is edited, does a prior approval still hold?) and a built-in default template.

That file does not exist in any branch or commit, so it could not be read. Both are real gaps here: this implementation says an id is "stable within the design" and stops there, and it makes you hand-write the YAML from scratch. Worth reconciling before building further.
