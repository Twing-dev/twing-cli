01 packages/core — the shared vocabulary

Types and pure functions everything else builds on. No I/O beyond reading config files. Imported by cli and server; mirrored by hand in the Go hook.

types.ts — the data model

Two families in one file, because they share TTL/id conventions and nothing else:

  • Path 1: Claim, CallEdge, Finding, Notice
  • Path 2: DesignStatement, DesignConstraint, DesignVerdict, DesignConflict, PendingReview

Read this one twice DesignVerdict’s doc comment is the single densest explanation of the system’s conflict model anywhere in the repo. It documents not just the four buckets but the values that were removed and why.

protocol.ts + framing.ts — the wire

Daemon socket messages and their encoding: a 4-byte big-endian uint32 byte length, then that many bytes of UTF-8 JSON. Needed because stream sockets coalesce and split writes; a length prefix is the simplest way to recover message boundaries. Frames are capped at 10 MB to guard against a corrupt prefix.

framing.ts is 45 lines and is the entire lesson on message framing.

There is exactly one wire format in this system. Nothing may invent a second — it’s enforced as a constraint in the repo’s own .twing/twing.yml.

Message types: enqueue, get_notices, session_end (hook → daemon); get_claims, get_identity, shutdown (CLI → daemon).

identity.ts — projectId, developerId

computeProjectId = sha256 of the canonicalized git remote get-url origin. Not a path — so the same project resolves identically across clones and worktrees. A repo with no remote falls back to a random id persisted in .git/twing-project-id, on the reasoning that no remote means no way to clone, so no cross-developer coordination need by construction.

The one hard cross-language invariant canonicalizeRemoteUrl here and canonicalizeRemoteURL in hook/identity.go must reduce every remote-URL form to the same string, byte for byte. This broke in production once — SSH and HTTPS clones of the same repo produced different projectIds and never saw each other’s work at all. The fixture table is duplicated verbatim in hook/identity_test.go for exactly this reason.

tree-sitter.ts + symbol-id.ts — symbol identity

Turns a file edit into a stable id like src/net/retry.ts::RetryPolicy.backoff. Parse with Tree-sitter, walk up from the edited range to the nearest named function / method / class declaration, and build <path>::<scope-path>.

Why it’s derived from tree structure and not line numbers: a symbolId built from AST ancestry survives line drift by construction. Someone adding an import at the top of the file doesn’t invalidate every claim below it.

Uses web-tree-sitter (WASM) rather than native bindings — no per-platform compile step across developer machines, at a parse-latency cost that doesn’t matter because parsing happens off the hot hook path.

v0 scope: TypeScript and JavaScript only. A full-file Write (vs. a localized Edit) falls back to a file-level claim with no symbol name — a known, deliberate gap.

manifest.ts / config.ts / gate-overrides.ts — state boundaries

Three files, three different scopes — worth keeping straight:

FileLives atScope
manifest.ts<repo>/.twing/twing.ymlCommitted. Shared with the team.
config.ts~/.twing/config.jsonMachine-local. A map of serverUrl → auth, not one slot.
gate-overrides.ts~/.twing/gate-overrides.jsonMachine-local, keyed by projectId.

Within the manifest, constraints and require_human_review are uploaded (seeded to the coordinator), while coordinator.serverUrl and capture are read purely locally and never transit. That distinction catches people out.

02 hook/ — twing-hook (Go)

A separate Go module producing one small binary. Spawned fresh per Claude Code hook event, does one trivial thing, and always exits 0 — a panic recovers silently, because a non-zero exit could look like a block.

Why Go, not TypeScript

Startup cost. It runs on every single tool call. A Node process start would blow the 50 ms budget on its own, before doing any work at all.

Why it mirrors instead of imports

No shared build, no cross-language toolchain — at the cost of a drift risk, managed by duplicating the fixture tables in the Go tests.

Two files deliberately carry real logic and are separately reasoned about — design_gate.go (verdicts) and daemon_launch.go (liveness).

03 packages/cli — command + daemon

Two things in one package: the user-facing command, and a background process.

twing admin / project / constraintsAccess control and project rules.
twing daemon / daemon restartForeground run; lifecycle management.

The daemon

One long-lived process per machine, shared across every repo — not one per project. It listens on ~/.twing/daemon.sock, acks immediately, and does the real work after the reply, so the accept loop is never blocked on parsing.

What it does per enqueue
  1. Resolve repo root, projectId, developerId (cached per repo)
  2. Read the file, parse with Tree-sitter
  3. Locate the edit point (Edit → find new_string; Write → whole file, no single point)
  4. Walk up to the enclosing symbol → symbolId
  5. Diff the signature against the daemon’s last-known parse of that file
  6. Update the repo-wide name index and the call graph
  7. Match the path against the manifest’s constraint globs
  8. Hand the Claim to the Syncer for batched upload

As of 2026-08-22 Read/Grep/Glob produce no Claim at all — they were pure noise downstream. State priming (steps 1–6) still runs for a read, which is what gives the next real edit an accurate signature diff.

Lifecycle: why so much machinery

Three things can start a daemon, and only one may evict a squatter:

  • An OS service (launchd LaunchAgent / systemd --user) — the primary path, installed by init, no elevation needed
  • A detached spawn — the fallback, and the only path on Windows
  • The hook’s self-heal on SessionStart, driven by ~/.twing/daemon-launch.json

Only the supervised instance may evict a process holding the socket. If any of the three could evict, they could evict each other in a loop — and launchd’s KeepAlive would happily feed that loop.

The bug all of this exists to prevent Every liveness check used to be a bare socket-connect probe, answering “is anything listening?” rather than “is it the process I just started?”. A daemon from a local checkout held the socket for 8+ days reporting a stale version while twing daemon restart printed success without touching it. Hence get_identity, the pidfile, and “success = a different pid holds the socket.”

Session capture (opt-in, local only)

When a repo sets capture: {enabled: true}, the daemon incrementally reads Claude Code’s own session transcript, keeps only human turns, assistant prose and touched file paths, redacts the result, and appends it to ~/.twing/sessions/<id>.jsonl. Nothing leaves the machine.

  • Watermark-based, not end-of-session — the session this was built against ran 11 days across three repos and produced zero commits
  • Opt-in by construction: absent means off. Installing an npm package must never start capturing on someone’s machine.
  • Four-layer redaction runs before anything is written: provider token prefixes, credentialed URIs, key=value secrets, then entropy scoring with a safe list for git SHAs and UUIDs

04 packages/server — the coordinator

Hono over Drizzle/SQLite. Owns all shared state and all verdict logic. One instance serves many projects and many developers. AGPL-3.0-only, unlike the other packages.

Middleware order is load-bearing Hono runs middleware in source registration order. CORS is mounted before auth so a browser preflight (which carries no Authorization header) doesn’t hit the 401 path; the version check is mounted before auth so a stale hook gets a specific 426 rather than a confusing “unauthorized”. Route matching is registration-ordered too — which is why /v1/designs/:id must be registered after /v1/designs/scope-match, or the bare :id segment swallows it.

05 Install & onboarding

The design goal: twing init is the only command anyone needs, whether they’re the first person to touch this project or the hundredth. 

npm install -g @twing/cli
cd my-repo
twing init
  1. init
    Find the repo root, read .twing/twing.yml
  2. init→you
    No coordinator configured? Prompt for one
    Defaults to the hosted server; a bare Enter accepts it
  3. init→coordinator
    Reachability check (GET /) before writing anything shared
    A typo here lands in a file every teammate inherits
  4. init→disk
    Write coordinator.serverUrl into .twing/twing.yml
    Comment-preserving upsert; refuses to clobber a different committed value
  5. Authenticate — the ladder
  6. init→GitHub
    OAuth device flow: “go here, enter code ABCD-1234”
    The GitHub token is used exactly once, then discarded — never cached
  7. coordinator→GitHub
    GET /repos/{owner}/{repo} — what can this person actually do?
    Verified server-side; never trusted as a client-supplied claim
  8. coordinator→init
    developerId + role — and if nobody has touched this project before, it is founded here
  9. init→disk
    Cache the minted PAT in ~/.twing/config.json
  10. Install the machinery
  11. init
    Install the twing-hook binary
    Local Go source wins first (a contributor may have uncommitted hook changes), then a prebuilt release fetch, then reuse whatever’s installed
  12. init
    Wire hooks into ~/.claude/settings.json — machine-global, once
  13. init
    If admin: write the install-enforcement hook into the repo’s committed .claude/settings.json
  14. init
    Install a launchd / systemd service, then start the daemon
    Service first — the reverse order raced two daemons for the same socket, and the systemd instance crash-looped forever under a reported “installed”
  15. init→coordinator
    POST /v1/constraints/seed — forwards this repo’s rules, and doubles as the founding trigger

The auth ladder, in precedence order

#ConditionResult
1--no-auth cached for this serverNothing to do — no identity exists on that coordinator
2A token is already cachedAuthenticated to the server — but check whoami for membership in this project, and GitHub-join if absent, reusing the same token
3--invite <code>Redeem it. Fully supported, no longer advertised.
4--no-githubSkip to the “no cached PAT” error
5defaultGitHub device flow — but only if the repo is GitHub-hosted (cheap local check, no network)

Why step 2 isn’t just “return the cached token” Found live: init in a second, never-founded repo on an already-onboarded coordinator returned the cached token immediately and skipped GitHub founding entirely. The org-based fallback then failed for anyone with no org membership — which is the default for anyone onboarded via GitHub founding in the first place.

Founding and roles

Role comes from real GitHub permissions, checked server-side against the caller’s own token — never a client-supplied claim, which would let someone with admin on an unrelated repo phish a role here.

maintain / admin

→ twing admin. Can found a new project, invite, decide reviews, edit constraints.

push / triage / pull

→ twing member. Can join an already-founded project, but cannot found one.

no access

403. The GitHub token doesn’t prove access to this repo.

A GitHub-founded project has no organization at all — orgId is null and access control is purely per-project, mirroring GitHub’s own model. Orgs still exist for the invite/bootstrap path.

Hook wiring is machine-global

Wired once into ~/.claude/settings.json, covering every repo from then on. This is why “gate off for this project” is a local override file rather than unwiring a hook — unwiring the global entry would disable the gate everywhere.

Nothing machine-local touches a working tree

Every runtime artifact lives under ~/.twing/ or the platform’s service directories. No .gitignore entry was ever needed, and no capture can be committed by accident.

Why a repo gets two hook mechanisms

A teammate who clones the repo and never runs twing init has zero hooks configured — twing would be entirely absent for them. So when an admin runs init, it also writes a small POSIX-sh hook into the repo’s committed .claude/settings.json.

  • Its only job is “is twing installed at all” — if yes it allows and gets out of the way; if no it denies with install instructions
  • Uses only git, test, grep, printf — no jq, node or npx on the steady-state path
  • $HOME stays a literal shell variable in the committed text, expanded on each developer’s own machine — unlike wireHooks’ baked-in absolute path
  • Deduped by a version-stamped marker prefix, so a future revision upgrades in place instead of duplicating
  • It must be committed and pushed by a human — twing cannot push on anyone’s behalf
