01 The problem

Several people — and several AI agents per person — work in the same codebase at the same time. Nothing tells them they’re about to collide until the collision is already in the diff, at which point it’s a merge conflict, or worse, two working implementations of the same thing that don’t conflict textually at all.

Git catches overlapping lines. It cannot catch “you both independently built a retry helper,” or “your signature change silently broke their caller,” or “you’re editing a file someone else’s plan already claims.”

twing sits at the moment of edit, not the moment of merge.

02 The one structural idea

Everything in this codebase follows from a single split. There are two code paths that share a data model but never share logic. Almost every “why is this written this way” question resolves to one of them.

Path 1
Capture / advisory §4 §11 §12

“Who touched what, and did anyone collide?”

Trigger
PostToolUse, SessionStart, UserPromptSubmit
Transport
Unix socket → daemon → HTTP (batched)
Budget
50 ms fire-and-forget
On failure
silent no-op fails open
Surface
twing align, injected notices
Entry
hook/main.go
Path 2
Design gate §17

“Is this agent allowed to edit right now?”

Trigger
PreToolUse, SessionEnd
Transport
HTTP, direct, synchronous
Budget
15 s lookup / 60 s LLM extraction
On failure
deny fails closed
Surface
allow / deny on the tool call
Entry
hook/design_gate.go

If you only remember one thing: the capture path is a dumb pipe that must never block, and the gate is the only thing in the system permitted to say no.

06 How to read the source

The comments in this codebase are unusually dense and unusually specific: most cite a date, a live incident, and what was tried and rejected. They are not decoration — several are the only record of why an obvious-looking simplification is wrong.

Source comments also cite section numbers (§4, §17, §17.9) constantly, referring to docs/orchestrator-and-verification-design-doc_v1.md. Those are design-time documents that argue for decisions; this site describes what was actually built.

Rule of thumb Read the comment before changing the code it sits on. When you add code, follow the convention: say what it does, and say what would break if someone “simplified” it.

Host

Claude Code

Not part of twing. It’s the agent runtime whose hooks API the entire system is built on — every twing behaviour is triggered by a Claude Code hook event.

  • Sends a JSON payload on stdin per event
  • Reads hookSpecificOutput from stdout for allow/deny
  • Merges hooks from user-level and repo-level settings — both fire
hook/ · Go, separate module

twing-hook

One small binary, spawned fresh per hook event, doing one trivial thing, and always exiting 0 — a panic recovers silently, because a non-zero exit could look like a block.

  • Why Go: startup cost. It runs on every tool call; a Node process start would blow the 50 ms budget on its own.
  • Capture handler forwards raw fields to the daemon and returns — it never parses toolInput.
  • Gate handler (design_gate.go) talks to the coordinator directly over HTTP, because that path needs an answer.
  • Mirrors @twing/core by hand rather than importing it — managed by duplicated fixture tables in the Go tests.
packages/cli/src/daemon/

The daemon

One long-lived process per machine, shared across every repo. Listens on ~/.twing/daemon.sock, acks immediately, and does the real work afterwards.

  • Exists so Tree-sitter parsing, signature diffing, call-graph maintenance and network sync never block a tool call
  • Batches claims to the coordinator on a ~7 s debounce; polls notices every 5 s
  • Survives restarts via a launchd / systemd user service, with a detached-spawn fallback and a hook-driven self-heal on SessionStart
  • Was once its own npm package; folded in when it turned out to have one consumer. Still a separate OS process.
packages/cli

The twing command

Thin server wrappers plus all the onboarding logic. The only piece a normal user interacts with directly.

  • init — the single onboarding step; safe to re-run
  • login / keygen / join — three ways to get an identity
  • align — the advisory report; falls back to computing claims from git diff when there’s no daemon at all
  • design / admin / project / constraints — gate and access-control surface
packages/server · AGPL-3.0-only

twing serve — the coordinator

Hono over Drizzle/SQLite. Owns all shared state and all verdict logic. One instance serves many projects and many developers.

  • /v1/claims, /v1/notices — the advisory path
  • /v1/designs/*, /v1/reviews/*, /v1/constraints/* — the gate
  • /v1/alignment-threads/* — the async reply channel between colliding developers
  • /v1/admin/*, /v1/projects/* — identity and access control
  • Current-state tables paired with an append-only activity_events log
packages/core

@twing/core — the shared vocabulary

Types and pure functions everything else builds on. No I/O beyond reading config files.

  • types.ts — the whole data model. Read DesignVerdict’s doc comment twice; it is the model.
  • protocol.ts + framing.ts — daemon messages, and the one and only wire format (4-byte big-endian length prefix + UTF-8 JSON)
  • identity.ts — carries the hard cross-language invariant
  • symbol-id.ts — turns an edit into src/net/retry.ts::RetryPolicy.backoff
  • manifest.ts, config.ts, gate-overrides.ts — committed vs. machine-local state
