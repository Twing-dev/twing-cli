01 A session that goes right

The agent uses plan mode. Registration is free and invisible, and nothing ever blocks.

  1. Plan mode
  2. Claude Code→hook
    PreToolUse · ExitPlanMode
  3. hook→coordinator
    POST /v1/designs/check { rawPlanText }
    60 s budget here, not 15 — this leg can run a real LLM call
  4. coordinator
    LLM extracts creates / touches / dependsOn / summary, then runs the checks against every other open design and the project’s constraints
  5. coordinator→hook→Claude Code
    allow verdict clean — “registered design <id>”
  6. Every edit, from here on
  7. Claude Code→hook
    PreToolUse · Edit
  8. hook→coordinator
    GET /v1/constraints/match?path=… → no match
    Ground truth: the literal file vs. project rules, independent of what any design claims
  9. hook→coordinator
    GET /v1/designs/scope-match?path=… → in_scope
    Also refreshes lastActivityAt — the one place real per-design activity is recorded
  10. hook→Claude Code
    allow
  11. After the edit — invisible, unblocking
  12. Claude Code→hook→daemon
    PostToolUse → one enqueue frame, fire-and-forget; the hook exits with empty stdout
  13. daemon
    Tree-sitter → symbolId, signature diff, call-graph edges
  14. daemon→coordinator
    POST /v1/claims, batched on a ~7 s debounce → findings (none)
  15. Session end
  16. hook→coordinator
    Best-effort close of every open design for this session
    Opportunistic tidying, not load-bearing — the TTL sweep is the backstop
ExitPlanMode is the happy path

Plan mode already produces exactly the artifact the gate needs. If the agent uses it, registration costs the developer nothing.

Two independent checks, in this order

constraints/match then designs/scope-match. The first exists specifically so a session can’t sidestep a project rule by registering an unrelated design first.

02 A session that gets blocked

If the agent skips plan mode, its first Edit reaches scope-match with nothing registered. The full pipeline, in order:

The five scope-match states

StateMeansOutcome
in_scopean open design covers this fileallow
no_designnothing registered for this session at alldeny → register a design
out_of_scopean open design exists, but none cover this filedeny → amend to add the file
flaggedsomething’s registered, but its own verdict wasn’t cleandeny → resolve the conflict
dormantonly a paused design covers this filedeny → explicitly resume it

Why flagged is checked before dormant A flagged design is an active block, possibly admin-gated, on work this session actually registered. A dormant design is just idle, parked work. Ranking “idle” above “actively blocked” meant a session carrying any dormant design could never learn about a real blocker sitting right next to it — it always got told to resume the dormant one, silently reactivating unrelated stale work while hiding the actual problem.

The shape of a deny

Every deny follows one three-layer grammar (denyMessage): a headline — one plain sentence, no identifiers, the only line most readers will read; why + details, indented, for whoever wants it; and “What now” with the exact commands.

Formatting constraints are real, not stylistic This string is JSON handed to Claude Code and read by the model. No ANSI colour (it would arrive as literal escape bytes and pollute the model’s context), no emoji, no box-drawing. Structure is the only formatting available — which is why prose is hard-wrapped in code rather than left to the terminal.

Every deny also carries a suffix addressed to the agent, telling it not to route around the gate silently and to say so explicitly if it resolves the block itself.

Five failure classes, each named

ClassSaysFix
No cached token“this machine isn’t signed in”twing login / twing init
401“your sign-in was rejected”Credentials expired or revoked → re-auth
403“you don’t have access to this project”twing join --github — a different problem entirely
Unreachable“can’t reach the coordinator”Check connection, retry
426“this machine’s twing-cli is out of date”npm i -g @twing/cli@latest && twing init && twing daemon restart

Why 401 and 403 are split Collapsing them cost a real user five days. The message said “your cached token is stale — run twing login”, but the actual cause was a 403: the developer simply wasn’t a member of that project yet, which twing login cannot fix.

One deny deliberately omits the escape hatch Four of the five offer TWING_DESIGN_GATE=off. The version-mismatch deny does not. A fresh Claude Code session, offered “update” and “disable the safety gate” as equally-weighted options, correctly refused to pick either and stopped to ask a human — a sign the option shouldn’t have been offered as a peer to the real fix. A version mismatch always has exactly one right answer: update.

The organising principle Approval belongs to whoever’s authority you’d be overriding. That single sentence is why three buckets block but only one needs an admin: a peer collision is yours to justify; someone else’s rule is not.

The three feeders of symbol_conflict
FindingFires when
textual_overlapAnother active write claim on the same symbol, from a different session and a different developer
contract_divergenceA signature changed, and a caller of that symbol has an active claim from someone else. Checked in both directions, so the finding doesn’t depend on submission order.
design_divergenceA real edit landed inside another session’s declared scope — no code on their side yet. The first place a Claim is checked against a DesignStatement.

All three originally included a single developer’s own two concurrent sessions. Reversed 2026-08-22 after live data: 14 of 14 self-pair alignment threads on this project sat open, unreplied, never acted on. A dedicated same-developer-multi-agent-drift feature is deferred, not rebuilt as a quieter variant.

Why the semantic comparator exists at all

Two designs describing a real, non-obvious conflict in unrelated-sounding words sail through the syntactic tiers as clean — those only compare literal path intersections. This asks the question they structurally can’t.

The prompt is empirically tuned, not guessed: validated against a 25-case labeled eval set plus four hand-authored full-scale plans with a deliberately hidden conflict. Three criteria (duplication, contradictory assumptions, tension), plus one explicit line countering the model’s persistent “different files ⇒ not a conflict” bias — banning the literal word “file” wasn’t enough, models reached for synonyms like “different layers” to preserve the same wrong heuristic.

It fails soft: one retry, then any error or unparseable response returns “no conflict”. Never invent a conflict because the model was unreachable.

    Registers a design: “add retry to HttpClient”

04 Alignment threads

A small, async, mailbox-style conversation between the two developers a finding names. A thread is a tiny current-state row; every message in it — including the auto-generated seed note — is an activity_events row, so history is genuinely append-only.

It is advisory, always

Closing a thread is unilateral — neither party needs the other’s agreement — and closing it does not by itself unblock anything. The block clears via twing design resolve --justify.

Who can see vs. who can act

Read: a party or a project admin. Reply/close: parties only. An admin can see every reconciliation in their project but can’t act inside one they’re not named on.

Why admins gained read access (2026-08-24)

Found live: a project admin whose dashboard login identity (from join-via-github, e.g. 206395444+someuser@users.noreply.github.com) differs from the developerId their own CLI sessions author claims under (a git-email-derived address) saw zero alignment threads in the dashboard — despite being the real party on several, from that exact PAT identity.

Not a bug in the party check, which is correctly symmetric. It was simply that the channel had no admin visibility at all once login identity and authoring identity diverge — which turns out to be the common case for anyone using both the CLI and the dashboard.

The fan-out bug class, fixed three times

Thread deduplication has been wrong on three separate axes, each found live:

  1. By symbol (2026-08-23). The dedup key included symbolId, so every new overlapping symbol between the same two developers forked another thread. One design pair accumulated 14 simultaneous open threads.
  2. By direction (2026-08-26). The semantic comparator is one-directional by construction, so A-checked-against-B and B-checked-against-A produced two threads for one disagreement. Fixed by also matching the reverse shape — requiring both design-id links, so two genuinely different conflicts sharing one side can’t merge.
  3. By status (2026-08-28). A closed or dormant thread was invisible to the match, so a new finding forked another one instead of reopening the existing conversation. Now it reopens — but only when at least one of the two designs behind it is still live.

Same lesson three times: a dedup key that includes too much forks; one that includes too little merges unrelated things. Both are visible only in production.

A reject is not a resolution When an admin rejects a review, the design closes terminally and nothing is appended to any justified-waiver list. The thread note says exactly that, rather than the old shared template which rendered “Resolved: X’s design was rejectd” — wrong grammar and wrong semantics at once.
