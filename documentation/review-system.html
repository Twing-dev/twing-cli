The review system

A change-time guardrail layer: once work is finished and committed, check that what was built matches what was declared, that the tests are real, and that the decisions hold up against what this project has already decided.

Read this as a proposal, not documentation The other six pages describe code that exists. This one does not. No part of this has been implemented — names, routes and table shapes are proposals and should be expected to change once someone builds it.

01 The problem, and the unfair advantage

LLMs write a lot of code, quickly. The bottleneck has moved: the responsibility now sits with whoever reviews it, and reviewing a thousand lines to decide whether everything is right is not a thing humans do well — or honestly, at all, past a certain size.

Every other review tool sees only the diff CodeRabbit, Greptile, Copilot review — all of them must infer intent from the code. That is circular: you cannot catch “this implements the wrong thing” when your only evidence for what it should do is the thing itself.

twing already has what they’re missing — declared intent, captured before the code existed, plus the record of everything that happened while it was written:

DesignStatement

Summary, creates/touches/dependsOn, and the full plan text. What they said they’d build.

Claims

Per-symbol records of what was actually edited, by whom, in which session. What they did.

Activity log

Every flag, justification, approval and alignment thread along the way. Why it happened that way.

Constraints

The project’s own ratified rules, already matched against paths.

Call graph

Who calls the changed symbols — blast radius, and which tests reference them.

Session transcript

Where capture is on: the actual conversation that produced the code.

The whole system should be designed around that. Diff-only is the degraded fallback — it still works (intent gets extracted from the changes), but the output must say so, because inferred intent is materially weaker evidence than declared intent.

02 The user experience

The hard question was never “what should it check” — it was when does it fire. In an agent session there is no natural “I’m done” moment.

Why the obvious triggers are wrong
TriggerVerdict
SessionEndNo. Sessions end because a laptop closed or context ran out. The capture subsystem already concluded this — SessionEnd is “a last drain, never the mechanism,” after a real session ran 11 days and produced zero commits.
Git commitWeak. Agents commit constantly; WIP commits are noise. The original spec deferred this trigger for a reason.
PR openRight audience, wrong moment. The agent’s context is gone by then. Keep it as a surface, not the trigger.
Manual onlyNecessary but insufficient. Nobody remembers. twing works today because it is ambient.

The signal already exists A design declares which files it will touch. When the diff shows all of them have changes, the work is plausibly complete — a computable signal nobody else has. That prompts the nudge; twing design close remains the explicit “I’m finished.”

Crucially this offers, never asserts — plans routinely over-declare, and work can be genuinely done without touching everything it named.

The four moments

  1. 1 · nudge→the agent, between turns
    Rides UserPromptSubmit additionalContext — the same channel coordinator notices already use. Fires once. Never mid-tool-call.
twing: this design looks complete — all 5 declared files have changes.

  Review it       twing review
  Or just close   twing design close --id 40025938
  1. 2 · run→the terminal
    Local checks are free and instant, so they print immediately. The coordinator’s LLM checks stream in after. Never a blank 30-second stare.
twing review · design 40025938 "Add exponential backoff to RetryPolicy"
  range  a1b2c3d..e4f5g6h  (merge-base with main)

  Local checks                                          0.4s
    ✓ scope         5 declared, 5 changed, 0 undeclared
    ✗ tests         RetryPolicy.jitter — no test references it
    ✗ tests         retry.test.ts:88 — asserts only toBeDefined()

  Coordinator checks                                    running…
    ✓ conformance   implementation matches declared intent
    ! precedent     contradicts constraint "all retries via RetryPolicy"

  2 blocking · 1 advisory
  1. 3 · fix→back into the agent’s context
    This is the whole product. Findings return through the same channel as the nudge, while the agent still remembers why it wrote the code.
twing review: 2 issues in the work you just finished.

  1  RetryPolicy.jitter has no test coverage
     You added jitter() and changed backoff(), but retry.test.ts
     references neither. The declared intent said "survive transient
     failures" — that behaviour is currently unverified.

  2  retry.test.ts:88 asserts nothing meaningful
     expect(result).toBeDefined() is the only assertion. It passes
     whether backoff returns 100ms or throws a string.

  Fix these, then re-run: twing review
  1. 4 · hand off→the PR, and twing-monitor
    For whoever reviews it and didn’t write it — which is the person whose problem this exists to solve.

Why moment 3 is the differentiator Every other reviewer comments on a PR hours later, when the agent has lost all context and a human must relay findings back. twing can hand findings to the agent while it still has the context that produced the code. The fix loop closes in seconds instead of hours — and it falls out of infrastructure that already ships.

Why it reviews committed code

Reviewing a commit range rather than a dirty working tree makes the review anchored to a SHA — reproducible, re-runnable, and linkable from twing-monitor. Two consequences:

  • twing review refuses on a dirty tree: “commit first.”
  • The range is merge-base(HEAD, main)..HEAD, not the last commit — a design’s work usually spans several. diff-claims.ts already computes exactly this range.

Turning it on

Opt-in in the file the team already commits, following the capture: precedent exactly:

# .twing/twing.yml
review:
  enabled: true
  block: false      # deterministic findings may block; off by default

twing init sees it and installs the review package. Nobody who doesn’t want it pays the install cost, and enabling it is a deliberate team decision.

03 Pipeline

The important property: the local pass always runs — with no coordinator and no LLM configured. Degraded, never broken.

04 Where the code lives

Separate repo, as intended — but with the client talking to one server only (the coordinator), reusing the existing PAT and server resolution. No second auth story, no second URL to configure.

PackageRepoUsed byContains
@twing/review-checkstwing-reviewclientDeterministic AST detectors. Pure functions, no network.
@twing/review-enginetwing-reviewcoordinatorPrompts, specialists, verification, adjudication.
/v1/change-reviews/*twing-cli—Routes, persistence, monitor feed.

Why the split falls here

Deterministic checks → client

They need the actual file contents, and Tree-sitter is already in @twing/core. Free, instant, offline, zero configuration.

LLM checks → coordinator

Credentials already live there (llm-client.ts’s ambient provider selection). No developer should have to configure Bedrock keys to review code.

Persistence → coordinator

Designs, claims and the activity log are already there, and twing-monitor already reads from it.

This also reduces version skew There are already three independently-updated deployables. Putting review logic in the coordinator means fixing a prompt is a redeploy, not an npm release every developer must pull. The separate repo still gets its own release cadence for the part that churns fastest.

05 Data model

Two new current-state tables plus one memory table, following the existing current-state-plus-append-only-log convention. Every raise / accept / dismiss also writes an activity_events row, so monitor’s feed needs no new plumbing. 

change_reviews
  id · projectId · branch · baseSha · headSha
  designIds (JSON)         -- may cover several designs
  developerId · status     -- running | complete | failed
  createdAt · completedAt
  UNIQUE(projectId, headSha)    -- re-running the same SHA returns the existing review

review_findings
  id · changeReviewId · projectId
  category     -- conformance | test_quality | bug | precedent
  detector     -- "test.untested-symbol" | "llm.conformance"
  severity     -- blocking | advisory
  confidence   -- high | medium          (LLM findings only)
  file · line · symbolId
  headline · detail · action             -- the existing three-layer grammar
  status       -- open | accepted | dismissed | fixed

review_policies                          -- memory across reviews
  projectId · detector · scope (glob) · reason · createdBy
  -- "always ignore this pattern here" — suppresses permanently

The UNIQUE(projectId, headSha) is load-bearing Re-running twing review on an unchanged commit returns the existing review instead of burning another round of LLM calls. Cheap idempotency, and it makes the command safe to run reflexively.

Naming collision to avoid PendingReview and /v1/reviews/* already mean “an admin approving a justified divergence.” Don’t overload them — ChangeReview and /v1/change-reviews keep the two concepts apart. Renaming the existing one across the CLI, the Go hook and the dashboard isn’t worth it.

Routes

06 The check catalogue

Every check — deterministic or LLM — has the same shape. Deterministic ones are pure functions over the bundle, testable with plain fixtures and no network, exactly as design-checks.ts is today. 

interface Check {
  id: string;                          // "test.untested-symbol"
  kind: "deterministic" | "llm";
  category: FindingCategory;
  severity: "blocking" | "advisory";
  run(evidence: EvidenceSlice): Finding[];
}

Ten of seventeen need no LLM at all That matters more than it looks. The deterministic set is fast, free, offline and has no false positives by construction — so it can block safely, and it runs even for a developer with no LLM provider configured. It also focuses the expensive calls that follow.

On “is the decision right or wrong” — the check I’d cut

Free-floating architectural taste from an LLM (“you should have used a queue here”) is the single highest-noise output this system could produce, and noise is what kills review tools.

There is a version that works: make it relational, not absolute — that’s what llm.precedent above is. Does this contradict a ratified constraint? A decision recorded in a past design or review on the same subsystem? Something a prior review already rejected? All of that is checkable against the activity log you already keep. “Is this a good decision” is not.

Ship the relational version. Drop the rest.

07 Evidence slicing

Never send the whole diff to one prompt One mega-prompt over a full diff produces a wall of confident findings, which is the failure mode this design exists to avoid. Each specialist gets a narrow slice, and they run independently — no shared context, so they don’t anchor on each other and genuine disagreement can surface.

SpecialistSeesNever sees
conformanceDesign summary + declared scope + per-symbol diff summaryTest files, unrelated symbols
test-semanticsOne changed symbol + the tests referencing itThe rest of the diff
bug-huntOne symbol before/after + its callers, via the call graphThe design
precedentDesign + matching constraints + prior decided reviewsThe diff body

Open problem: bundle size A large PR can produce a bundle too big to slice cheaply. Proposal: cap it at the top-N symbols by blast radius (the call graph gives you that ordering for free) and say so in the output — “reviewed 20 of 47 changed symbols, ranked by callers” — rather than silently truncating. Silent truncation in a tool people trust to catch things is worse than no tool.

08 Verification — where false positives die

Every candidate finding gets a second call that sees only the finding and the specific code it names, asked one question: does this actually hold?

Non-survivors are deleted, not downgraded to “possible issue.” Softening a finding you couldn’t confirm is how a review tool teaches people to skim past its output.

This is the same discipline the semantic comparator already uses — validated against a 25-case labelled eval with zero false positives as the acceptance bar. Without it, this product dies of noise within a month.

You are your own eval corpus This repo has months of merged PRs, the designs that produced them, and an activity log of what the human reviewer actually caught. Backtest: feed a merged PR its own design and see whether the reviewer finds what was really found. Most people building this have to hand-label from scratch.

09 What blocks, and what fails how

Mirrors the split that already exists — file_overlap advises, constraint_violation blocks — for the same reason: one is a heuristic, the other is a stated rule.

Deterministic → may block

Facts, not guesses. “Four changed symbols with zero test references” is checkable. Still opt-in per project.

LLM → always advisory

Never stop a merge on a probabilistic claim.

Default → nothing blocks

twing already blocks at edit time. Earn the right to block at merge time.

Failure modes — all soft

FailureBehaviour
No LLM provider configuredLocal findings only, stated plainly
Coordinator unreachableLocal findings printed, not persisted
One specialist errorsIt yields nothing; the others continue
Verification call errorsThe finding is dropped — safer than emitting it unverified
No design foundExtract intent from the diff, label it inferred
Dirty working treeRefuse, with “commit first” — the one hard precondition

Note the inversion from the gate: the gate fails closed because a silent allow is indistinguishable from a bypass. Review fails soft because a missed finding costs a review, while a false block costs the whole team’s trust.

10 The payoff: review feeds the gate

This is what makes it more than a linter, and it’s the reason to build it here rather than anywhere else. 

review finding  ──►  a human accepts it  ──►  recorded
                          │
                          │  (same finding accepted N times across PRs)
                          ▼
                 propose a constraint  ──►  an admin ratifies it
                          │
                          ▼
        the GATE now blocks it at edit time — before the code is written

The hook for this already exists ConstraintStore.add already accepts source: "ratified_from_divergence:<designId>". The schema anticipated this loop; nothing has filled it yet.

Findings a human dismisses are recorded too, and never resurface for that pattern — that’s review_policies. So the system gets quieter as it learns, rather than louder.

Net effect: constraints get ratified from observed reality instead of written speculatively upfront — which is exactly the failure mode this repo already documented when it pruned six constraints that named real invariants nobody could enforce per-edit without the check degrading into a rubber stamp.

11 Build order

Ordered to test the riskiest assumption first: does having the design actually make review better than diff-only? Progress saves locally.

0 / 0 · 0% reset
1 · twing review skeleton

Preconditions (clean tree), range resolution, design lookup, evidence bundle assembly. Almost entirely reuse of diff-claims.ts and existing stores.

2 · One deterministic check: test.untested-symbol

Changed symbol with no test reference. No LLM at all. Uses the call graph that already exists. Shippable on its own, and it tells you fast whether the signal is real.

3 · Persistence + monitor list view

change_reviews, review_findings, the routes, and a paginated list. Same shapes as every other listing in the dashboard.

4 · One LLM check: llm.conformance, with the verification pass

The verification pass ships with the first LLM check, never after. It is not an optimisation — it’s what makes the output trustworthy enough to read.

5 · The eval harness, backtested on this repo

Before adding check six. Merged PRs + their designs + what the human actually caught. Zero false positives as the bar.

6 · The rest of the deterministic set

Cheap to add once the harness exists, and each one reduces the LLM surface.

7 · The nudge

Design-completion detection → additionalContext. Deliberately late: don’t make it ambient until the output is worth interrupting for.

8 · Findings back into the agent’s context

Moment 3 — the actual differentiator. Small once everything above exists.

9 · review_policies and constraint ratification

The compounding loop. Last, because it needs real dismissal data to be worth anything.

12 Open questions

Should design close auto-run review?

Auto is more ambient, and ambient is what makes twing work — but it spends money and 30 seconds on every close, including trivial ones. I lean offer, but it’s a genuine toss-up.

Branch-scope or design-scope?

A branch often spans several designs. Suggestion: branch for the PR surface, design for the in-session surface — same findings, different framing.

Designs closed without review

Monitor could surface “review debt.” Nobody else could compute it. Genuinely useful, or just another nag?

Bundle size caps

Top-N by blast radius is the proposal, but N and the ranking function both need real data to set.
