01 Overlap short-circuits the constraint check

correctness confidence: high not a security hole design-checks.ts:461

runDesignChecks returns tier 1 before ever reaching tier 3:

const structuralConflicts = structuralOverlaps(candidate, others);
if (structuralConflicts.length > 0) {
  return { verdict: "file_overlap", conflicts: structuralConflicts, constraints: [] };
}
const constraintHits = constraintMatch(candidate, constraints);   // ← never reached
if (constraintHits.length > 0) {
  return { verdict: "constraint_violation", conflicts: [], constraints: constraintHits };
}

Why this used to be fine, and no longer is

When file_overlap still blocked (before 2026-08-19), short-circuiting was harmless: you were denied either way, so which reason came back first didn’t change the outcome.

Once tier 1 was demoted to advisory-only, that stopped being true. A design that both overlaps another design’s declared paths and violates a project constraint now returns file_overlap — and app.ts only calls designs.flag() on constraint_violation. So the design stays open, and the constraint is never surfaced at registration.

Not a hole The §17.9 ground-truth backstop (GET /v1/constraints/match) still catches it on the actual Edit/Write — which is precisely what that backstop exists for. Nothing gets through.

But the message is wrong The ExitPlanMode registration reports “allow, registered” instead of naming the protected rule. The developer discovers the constraint later and less legibly, at a point where the plan is already written.

There is direct precedent in the codebase

app.ts hits this same ordering problem on the resolve path and works around it explicitly. From that route’s own comment (design 7d65230f, 2026-08-17):

“Originally derived this from checkAmendedScope’s overall verdict — wrong, because runDesignChecks returns tier-1 overlap before it ever reaches tier-3’s constraint check, whenever both happen to be true at once. Found live: this design genuinely touched require_human_review paths and happened to overlap another open design on those same files — the recomputed verdict came back ‘overlap’, constraintId was silently dropped, and the approved review never populated justifiedConstraintIds … the exact bug this design was registered to fix, reproducing itself.”

The fix there was to call matchConstraintsForPaths directly rather than trust the top-line verdict. The registration path never got the equivalent fix.

Test coverage

design-checks.test.ts:106 exercises tier 3 with openDesigns: [] — so no test covers the combination at all. That’s what makes this a good first contribution: write the failing test before deciding on a fix.

Three possible shapes for a fix — none obviously right
  1. Check constraints first. Simple reorder. But it inverts the documented “cheapest first” tier ordering, and a blocking verdict arguably should outrank an advisory one anyway.
  2. Return both. DesignCheckOutcome already carries conflicts and constraints as separate fields — populate both, and let the caller decide which is the headline. Most information preserved; largest blast radius across callers.
  3. Leave it. Argue the backstop is sufficient and this is only a message-quality issue. Defensible — but then the tier-1 early return deserves a comment saying so, because right now it reads as an oversight.

This is a judgement call about the model, not a mechanical bug. Worth a decision from whoever owns §17.

02 Version skew is the normal state

architecture confidence: high observed live

Three artifacts deploy on independent schedules, and nothing forces them into step:

ArtifactContainsUpdated by
@twing/clithe CLI and the daemonnpm install -g
twing-hookthe capture edge and the whole gateonly twing init — a separate GitHub release fetch
twing serveall verdict logic and statewhenever someone redeploys

Four separate mechanisms exist purely to manage that:

The 426 middleware

Every gate call sends x-twing-hook-version; a mismatch returns 426 Upgrade Required before auth even runs, so “you’re out of date” beats “unauthorized” when both are true.

Snapshotted daemon version

daemonVersion is captured at module load and never re-read — because npm install -g overwrites the very package.json a running daemon would read, so a stale process would report itself current.

Direction-aware messaging

compareVersions distinguishes “this machine is behind” (update) from “the coordinator is behind” (wait) — npm cannot move backwards, so the update instruction would be nonsense in the second case.

Never-backfill schema

Optional columns and absent-tolerant readers are what let an older coordinator and a newer client talk at all.

The trap this creates, recorded live 2026-08-27 npm install -g @twing/cli@latest && twing daemon restart looks like the fix and does not touch the hook binary — ensureHookInstalled() only runs as part of twing init. A session that followed that exact two-step instruction still failed the retry, because the hook is what actually sends the version being checked. The deny message now says npm i -g … && twing init && twing daemon restart for that reason.

Observed on the live coordinator

While working in this repo, a real deny rendered flaggedLeadAndDetail’s generic fallback lead (“twing compared your plan against other active sessions and found a conflict”) while simultaneously setting requiresAdmin: true.

In the current source both derive from the same field, blockedReason — so that combination is impossible from a same-version server. It means the coordinator sent requiresAdmin but not verdict, i.e. it predates the 2026-08-26 verdict field.

User-visible consequence An llm_divergence block is supposed to be self-approvable — resolve --justify clears it instantly, no admin. The live server is telling people it needs a project admin. Worth confirming against the deployed version.

03 Alignment threads are accumulating

operational confidence: medium needs a look, not necessarily a fix

twing align threads --status open on this project returns roughly twenty open threads. The majority are scope_intrusion rows between two developers, generated from a single session, all naming files under packages/server/src/ — one thread per file.

That pattern is close to what the 2026-08-23 dedup redesign was built to stop: the findOrCreate key dropped symbolId precisely because one design pair had accumulated 14 simultaneous threads, one per touched file.

Why this may be correct behaviour rather than a regression

Two readings, and the evidence doesn’t settle between them:

  • Pre-fix rows. These threads may simply predate the redesign. Nothing backfills old rows, so they’d persist in their original one-per-symbol shape forever.
  • A different axis. The dedup key is (developerId, otherDeveloperId, designId). If each finding resolved a different designId on the other side, forking is correct by the current key — and would indicate the other session had many open designs rather than one.

Checking openedAt on those rows against the 2026-08-23 change date would distinguish the two in about a minute. Either way, closing the stale ones costs nothing — closing is unilateral and non-blocking.

04 Smaller observations

Inconsistent repo-root resolution in handleSessionEnd
cosmeticconfidence: highno bug today

handleEditWriteGate deliberately uses config.RepoRoot rather than payload.Cwd, with a comment explaining why: it’s already the resolved canonical root, so it avoids a second, potentially divergent git shell-out and stays correct when cwd isn’t the repo the edited file lives in.

handleSessionEnd, a few dozen lines below, calls computeProjectID(payload.Cwd) instead. Harmless in practice — that path only runs after resolveServerConfig(cwd) already succeeded, which means cwd is inside the repo — but it’s the one call site that didn’t get the treatment, and it will read as an oversight to the next person.

A stray attribute typo in this documentation set
self-reported

Noted for honesty rather than importance: these pages were hand-authored, and at least one data-s attribute was initially written as data-s". It has been corrected, but if you find page filtering skipping a block, a malformed attribute is the likely cause — the filter only sees elements carrying a clean data-s.

Soft claims are dead weight on the wire
cleanupdeliberate, documented

Claim.stage still admits "soft", and stageForTool still computes it — but as of 2026-08-22 the daemon, the only live producer, never constructs one. Both are kept deliberately (the doc comments say so) in case a future producer legitimately emits one.

Worth knowing so you don’t “clean up” a type that’s intentionally wider than its current use.

The multi-repo ExitPlanMode path is prefix-matched
design limitdocumented

When cwd isn’t itself a git repo, the hook treats each immediate child directory as a candidate project and partitions the extracted plan by directory-name prefix. A plan that names no concrete path inside any candidate denies with “can’t tell which project this belongs to” — deliberately, rather than guessing.

The limitation to know: matching is one level deep and purely textual. A plan that refers to files without repo-prefixed paths won’t match anything, even when a human would know exactly which repo it means.

05 What is notably well built

Findings pages skew negative by construction. For balance — these are the parts that stood out as unusually solid on a full read.

The comment discipline

Most non-trivial comments cite a date, a live incident, and what was tried and rejected. Several are the only surviving record of why an obvious simplification is wrong. This is rare and genuinely valuable.

Failure-mode reasoning

Fail-open vs. fail-closed is decided per path with an explicit argument, not by default. The reversal of §17.7’s original fail-open recommendation is documented with the reasoning that drove it.

Deny messages as a product surface

Three-layer grammar, rendering constraints written down, the 401/403 split, and the removal of the escape hatch from the version deny after watching an agent stall on it.

The four-bucket model

Collapsing five verdicts, three constraint types and a severity field into four buckets governed by one principle removed a large amount of accidental complexity — and the doc comment records exactly what was checked before doing it.

The daemon-identity work

Replacing “is anything listening?” with “is it the process I started?” across every liveness check, after an 8-day orphan. Eviction is constrained three ways to avoid becoming a worse bug than the one it fixes.

Empirical thresholds

PLAN_RETRY_SIMILARITY_THRESHOLD was measured, not guessed — with the sample scores recorded in the comment, and a note that a first instinct of ~0.9 would have missed the real case.
