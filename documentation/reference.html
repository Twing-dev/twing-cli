The one hard cross-language invariant canonicalizeRemoteUrl (core/identity.ts) and canonicalizeRemoteURL (hook/identity.go) must reduce every remote-URL form to the same string. If they drift, projectId silently diverges between the hook and the daemon/CLI. This broke in production once — SSH and HTTPS clones of the same repo never saw each other. The fixture table is duplicated verbatim in hook/identity_test.go.

What canonicalization actually does
  1. SCP-like SSH syntax git@host:org/repo → host/org/repo
  2. Otherwise strip scheme://[user@]
  3. Strip a trailing .git
  4. Strip trailing slashes
  5. Lowercase the whole thing

Lowercasing is deliberate: hosts are case-insensitive and GitHub-style paths route case-insensitively, so a false negative (a missed cross-session match) is worse than over-normalizing.

The identity split you will run into

The daemon computes developerId locally from git config user.email. The server resolves it from the authenticated PAT. These routinely differ — a GitHub-login identity like 206395444+user@users.noreply.github.com vs. a git-email one.

That divergence is why alignment threads gained admin read visibility, and it’s the first thing to suspect when someone says “the dashboard shows me nothing.”

02 What’s durable, what isn’t

Durable — real tables

designs, pending_reviews, constraints, alignment_threads, and the identity tables (organizations, org_memberships, project_records, project_memberships, developers, invites).

Because they can’t be reconstructed from anywhere else.

In-memory only

Claims, CallEdges, and undelivered notices — held in Store’s Maps, durable only as activity_events rows.

Because every daemon keeps its own local history and re-reports on the next flush, so the shared view rebuilds itself within seconds of a restart.

The append-only log activity_events gets one row per state transition, written in the same call that makes the transition — there is no separate replay or projection step. It is insert-only by convention: no store method in the codebase issues UPDATE or DELETE against it, and none should be added. It spans both the §4 and §17 families, and is the one place the “share a data model but never share logic” rule is deliberately crossed.

Portability discipline in the schema

Every column is text or integer only — JSON fields are text-serialized, timestamps are epoch-ms integers, booleans are 0/1. No SQLite-only column type is load-bearing and nothing uses a SQLite-specific pragma or expression, so a parallel Postgres schema can reuse the same names and shapes later.

TWING_DB_DRIVER=postgres is a documented seam that throws rather than silently falling back to SQLite — a misconfiguration should be loud, not a silent downgrade.

Never backfill

When a table gains a column, pre-existing rows are left without it and readers handle its absence. You’ll see this everywhere: category/subKind on threads, blockedReason on designs, symbolIds falling back to a legacy singular symbolId.

This isn’t laziness — it’s what makes version skew survivable across three independently-updated deployables. See Findings.

Dormancy is not cosmetic It is the fix for unbounded O(n²) pairwise comparison growth. openDesigns() excludes dormant designs, and that exclusion is the entire reason the state exists. A dormant design is never woken silently: a file matching its scope produces a deny pointing at twing design resume, because a file match isn’t proof of intent to resume — a long-lived session can register design A, abandon it, and later touch a file A happens to cover for unrelated reasons.

Approval memory — four separate lists, deliberately not merged

runDesignChecks re-evaluates a design’s entire merged scope on every amend — not just the new delta. Without approval memory, anything once approved would re-flag forever.

FieldKey shapeWaives
justifiedConstraintIdsbare constraint idconstraint_violation
justifiedOverlapsdesignId::pathfile_overlap
justifiedConflictsbare designIdllm_divergence — no path to key on
justifiedSymbolConflictsdesignId::symbolIdsymbol_conflict

The last two share a key shape but stay separate on principle: a row-2 advisory waiver’s history must never be conflated with a row-3 block’s. All four are appended to on approve only — a reject settles nothing.

Overlap waivers are keyed per specific path, not per design pair: waiving one file’s collision must not silently swallow a different file added later between the same two designs.

05 .twing/twing.yml

The one committed, team-shared config file. Every key is optional.

coordinator:
  serverUrl: https://coordination-server.twing.dev   # read locally, never uploaded

constraints:                                          # uploaded (seeded) verbatim
  - text: "All retries go through RetryPolicy"
    scope: "src/net/**"

require_human_review:                                 # also uploaded, same mechanism
  - path: "packages/server/src/identity-store.ts"
    reason: "auth/identity resolution — a bug here is an access-control hole."

capture:                                              # read locally, never uploaded
  enabled: true                                       # opt-in; absent means off
KeyUploaded?Effect
coordinator.serverUrlnoWhere everything else is sent. Read by the CLI and the Go hook.
constraints[]yesSeeded to the Constraint Store → constraint_violation on match
require_human_review[]yesSame mechanism, different name — both seed as type "constraint"
capture.enablednoTurns on local conversation capture. Opt-in; absent = off.

A constraint is expensive — spend it carefully Every entry blocks the edit and needs a project admin to approve the override. It also cannot check what it claims to check: the gate matches a path and denies, it never reads the diff. So a rule buys exactly one thing — “stop, and make an admin look” — worth paying for only where the path is edited rarely and a bad change would be silent. This repo pruned six rules on 2026-09-06 for failing that test: they named real invariants, but ones already covered by tests, on files edited 20–39 times, where a per-edit admin round trip degrades into a rubber stamp.

Editing a reason: string does not update the rule ConstraintStore.add upserts on the exact statement text. Changing it creates a second constraint alongside the old one. Put explanatory notes in YAML comments, not in reason:.

Provider selection is ambient — there is no TWING_LLM_PROVIDER. The first credential present wins, in the order above, and selectProvider throws when none is set. That throw reaches a caller that fails soft, so a server with no LLM configured still runs; it just never blocks on a plan-text check.

07 The eight invariants

When something looks odd, it is usually one of these.

01
The capture hook never denies

And it always exits 0. A panic recovers silently — a non-zero exit could look like a block. Enforced as a constraint in the repo’s own manifest.

02
The capture hook has no decision logic

It forwards toolInput verbatim and never parses it. One sanctioned exception: daemon_launch.go’s self-heal.

03
The gate fails closed

Against a configured coordinator. A silent allow on auth failure is indistinguishable from someone deleting their own token to bypass it. “No coordinator” and “file outside the repo” are not failures — those are silent allows.

04
Exactly one wire format

Nothing invents a second.

05
developerId is always the authenticated identity

On every write. Never a client-supplied field — whatever a client sends is ignored, not merely validated.

06
Approval belongs to whoever’s authority you’d override

Peer collisions are self-approvable. Project rules need an admin.

07
Append-only; never backfill

New columns leave old rows alone; readers handle absence. This is what makes version skew survivable.

08
Anything that blocks says why, and what to do next

A deny message is a product surface, not an error string.
