Developer guide · source snapshot · 9 October 2026

One shared toolbox.
Three different flows.

@twing/core gives the CLI, background daemon, and coordination server the same definitions and helper functions. It helps them agree on which project, which code, what was planned, and what messages mean.

The most important distinction: core is a library, not a running service. It exposes TypeScript/JavaScript APIs through src/index.ts. It does not register HTTP routes, start a daemon, store designs in a database, or make conflict decisions by itself.

1. Record edits

After an edit, record which file or function changed. Core supplies parsing, symbol names, identity, and message formats. This is background evidence, not a blocking conflict check.

2. Check a design

Before an edit, require a usable plan covering the file and check project rules. Core supplies plan validation and data contracts. The hook and server decide whether to allow it.

3. Capture conversation

When opted in, keep human messages and assistant prose, remove tool content, and redact likely secrets. Core does the filtering; the daemon handles consent, storage, and uploads.

Based on all 18 modules re-exported by packages/core/src/index.ts, plus the CLI/daemon/server call sites. Package version: 1.3.19-experimental.1; core requires Node >=22.5. Older comments and legacy types are not treated as proof of current behavior.

Where core fits

AI coding session (Claude Code / OpenCode / Codex)
  │
  ├─ BEFORE edit → hook → HTTP → coordination server → allow / deny
  │                            ↑
  │                      core's shared models
  │
  ├─ AFTER edit → hook → local socket → daemon → HTTP → server
  │                                     ↑
  │                          core parses / names / frames
  │
  └─ Prompt / session events → daemon reads transcript
                                 → core filter + redact

Think of core as the shared vocabulary and reusable tools. The CLI is the control panel, the hook is the messenger/checkpoint, the daemon is the local worker, and the server is the team coordinator.

Words you will see everywhere

WordSimple meaning
projectId“Which repository?” Normally a SHA-256 hash of the normalized origin URL, so SSH and HTTPS clones of the same repo agree.
developerId“Who is doing the work?” Core can suggest a local label from git email. In normal authenticated server requests, the server trusts the token-resolved identity instead, not a supplied label.
sessionId“Which AI conversation?” Separates multiple sessions belonging to the same developer.
symbolId / design target“Which piece of code?” Shared spelling: src/net/retry.ts::RetryPolicy.backoff. With no identifiable symbol, just src/net/retry.ts.
ClaimA receipt saying a session touched a file/function, when, on which branch, and optionally how its signature changed. Not the source-code body.
DesignStatementA plan registered on the server: goal/summary, plan text, declared changes, file scope, owner, session, and lifecycle state.
DesignConstraintA project rule tied to paths or symbols. A matching rule can require admin approval; matching does not analyze the code diff.
PendingReview vs DesignCommentA PendingReview is an approval request to override a block. A DesignComment is a person's discussion on a design. These are different workflows.
CallEdgeA “function A might call function B” link, based on names and locally observed files. Not a full compiler/type-resolved call graph.
Manifest vs machine configManifest: committed repo settings in .twing/twing.yml. Machine config: credentials per coordinator in ~/.twing/config.json.
Coordinator / TTL / ASTCoordinator = team server. TTL = how long something stays active. AST = the code's parsed structure, used to find functions instead of relying on line numbers.

Use-case flows, step by step

Green route names below belong to packages/server, not to core. The named helper functions belong to core unless explicitly labeled otherwise.

1 · Set up a repository

Situation: you run twing init so a repo can coordinate AI work.

  1. Find the repo with findRepoRoot; compute project identity using computeProjectId. GitHub helpers can identify its owner/repo.
  2. CLI auth resolution chooses the coordinator (explicit flag, then environment, then repo manifest). Core normalizes URLs and reads credentials with readConfig / getServerAuth.
  3. The CLI handles joining/authentication when needed. Core does not mint tokens or decide project membership.
  4. upsertCoordinatorServerUrl sets the committed coordinator without silently replacing a different one. loadManifestFromFile reads rules and settings.
  5. The CLI installs/wires the hook and starts the daemon. Core generates reusable committed bootstrap content through bootstrapHookScript and mergeBootstrapHookEntries.
  6. The CLI seeds rules/settings via POST /v1/constraints/seed using authFetch. Server permissions decide whether this is allowed.

Result: the repo knows its coordinator; this machine has the local tools/auth it needs. Session capture remains off unless the repo explicitly enables it.

Call sites: cli/init.ts, cli/enforce-hooks.ts.

2 · Register a plan before coding

Situation: an agent wants to modify retry behavior and registers a YAML design template.

  1. CLI reads the file; templateSyntaxError checks YAML syntax. parseDesignTemplate produces a goal, optional plan, and changes.
  2. validateTemplate reports all problems: missing goal/plan/changes, unsupported action/kind, duplicates, placeholders, and invalid from usage.
  3. deriveScope extracts file paths from targets. add goes into creates; all other actions go into touches. Each list is deduplicated.
  4. CLI sends structured scope, changes, and architecture text to POST /v1/designs/check through authFetch.
  5. The server registers the design and synchronously checks project rules. A separate asynchronous semantic comparison can later find conflicting/duplicate intent and flag designs.

Result: the design has a stable ID. A clean response is not a promise that a later semantic pass will never flag it.

Plan-mode variant: Claude Code's ExitPlanMode hook can send plain plan text for server-side extraction. OpenCode and Codex fall back to explicit registration after a first-edit denial; core does not implement harness adapters.

Call sites: cli/design.ts, server/app.ts, hook/design_gate.go.

3 · Ask “may this edit happen?”

Situation: an agent is about to edit src/net/retry.ts.

  1. The Go hook resolves the repo/coordinator and cached credentials. A local gate override can switch off this repo's design gate; core's setGateDisabled writes that override.
  2. The hook talks directly to the server, not through the daemon. GET /v1/designs/scope-match checks this project's session and file against usable design scope.
  3. An open design covering the file gives in_scope. Other outcomes include no_design, out_of_scope, flagged, and dormant.
  4. GET /v1/constraints/match checks the actual file against project rules, independently of the registered plan. Applicable approvals are considered server-side.
  5. The hook returns the allow/deny response to the coding harness. Review-comment acknowledgement and version checks are additional hook behavior, not core template validation.

Result: an in-scope, unblocked edit can proceed. Missing scope calls for registration/amendment; dormant work needs resume; constraint blocks need admin review.

Against a configured coordinator, auth/network/parse failures fail closed: the hook denies rather than pretending the check passed. A repo with no coordinator configured is a different case: it is not gated.

4 · Record the edit that actually happened

Situation: an edit successfully changes RetryPolicy.backoff.

  1. The hook sends an EnqueueMessage over defaultSocketPath(). encodeFrame / FrameDecoder.push preserve JSON message boundaries.
  2. The daemon acknowledges promptly, then runs its own extractClaim pipeline in daemon/claims.ts.
  3. Core locates the repo and identity. parseSource parses the current file; findEnclosingSymbol finds the function around the edit point.
  4. computeSymbolId creates src/net/retry.ts::RetryPolicy.backoff. The daemon compares old/new signatures when it has a previous version.
  5. matchConstraints attaches local rule-match IDs. Symbol enumeration and updateCallGraph update locally observed call relationships.
  6. The daemon constructs a Claim, batches it, and sends claims/new edges to POST /v1/claims. The server stores evidence; the monitor can read it back.

Result: evidence of what was edited. No current claim-vs-claim conflict detection: those checks were removed on 1 October 2026, and this route's findings are empty.

Fallbacks: whole-file Write, unsupported language, imports/outside a named function, or a missing edit-point match yields a file-level symbol ID. Read can prime the parser cache but produces no live claim; Grep/Glob also produce no live claims.

Call sites: daemon/claims.ts, daemon/server.ts, daemon/sync.ts.

5 · Change, pause, finish, or resolve a design

  1. New files needed: amend the design. Template validation can omit the existing goal/plan on an amendment; new declared changes derive additional scope. The server rechecks the merged scope.
  2. Work went idle: the server makes the design dormant after its active inactivity window (default seven days). Explicit resume re-runs checks; core only defines constants and types.
  3. Peer intent conflict: adopt another design (this one becomes superseded) or justify a divergence. With no outstanding constraint hits, the current server auto-approves that justification.
  4. Project rule hit: justify it, then wait for a project admin to approve/reject the PendingReview. Approval records specific waivers so the same settled rule does not block every amendment again.
  5. Done: close the design explicitly or through session-end handling. Its ID/review link remains meaningful afterward.

Lifecycle gist: open → dormant → expired on inactivity; dormant → open on checked resume; open → flagged on a block; approved resolution can reopen it; close/adopt finish or supersede it. Default dormant retention is another seven days from becoming dormant.

Linked multi-repo work: designs can share a groupId. Summary amendments and closing propagate across the group; file scope and rule approvals stay project-specific. This is server-store behavior, not a core function.

6 · Capture an opted-in conversation

  1. The repo has capture: { enabled: true }. captureEnabled recognizes only literal boolean true, not a string or a missing setting.
  2. A prompt/session event sends get_notices or session_end with a TranscriptSourceDescriptor. The daemon's source adapters read Claude JSONL, OpenCode SQLite, or Codex rollout data and normalize entries.
  3. The daemon determines consent and where capture may begin. reposForEntry helps attribute real tool paths to repos instead of treating every entry's cwd as a new repo touch.
  4. filterTranscriptEntry keeps human text, assistant prose, and selected file paths. It drops tool inputs/results as content, thinking, images, metadata turns, compaction summaries, and harness-injected noise.
  5. redact masks likely credentials in retained conversation text. The daemon appends records to ~/.twing/sessions/<sessionId>.jsonl and saves its source cursor.
  6. The uploader reads the durable local capture and sends new content via POST /v1/captures, with retry progress tracked per session/server.
Consent is sticky for the session. Once an opted-in repo qualifies it, later conversation can include work on repos that did not opt in. Capture reaches backward only to its consent boundary (or session start for an opted-in cwd). This is not a per-repo privacy filter.

Current storage distinction: there is no public GET/DELETE capture route. However, server-side design chat/resynthesis can use captures internally as context; “nobody reads captures” is no longer accurate.

Call sites: daemon/transcript.ts, daemon/capture-upload.ts, server/design-context.ts.

7 · Receive a review reminder and add a commit link

  1. A person leaves a DesignComment in the monitor, optionally anchored to quoted plan/summary/change text. People answer comments; comments are not an automatic agent answer.
  2. The daemon polls GET /v1/review-queue and active designs. buildDesignReviewUrl builds dashboard links from the configured/published monitor URL.
  3. A NoticesMessage returns durable openReviews, ordinary notice items, optional version mismatch information, and designLinks to the hook.
  4. The hook reminds the session/user about reviews; it can require a one-time acknowledgement for the edited project. It sends the fact/IDs/link, not the reviewer's comment body.
  5. The agent is asked to add Twing-Design: <review-url> to its commit message. Core defines DESIGN_TRAILER_KEY; it does not run git or insert trailers.

Separate feature: the dashboard's private design chat is model-backed and grounded server-side. It is not the same as a person's review comment.

8 · Bootstrap without a local CLI / inspect the daemon

GitHub App setup: server-side setup uses computeProjectIdForGithubRepo, renderManifestWithCoordinator, and the same bootstrap script/settings generators as the CLI. It writes onboarding files via GitHub APIs; core itself only returns content.

Daemon administration: the CLI frames a get_identity message; the daemon returns PID, startup version, and start time. A shutdown message gets shutdown_ack, then daemon-owned flush/exit behavior. Core only supplies the contracts and frame codec.

Read cached claims: get_claims remains supported by the socket protocol. Its daemon handler scopes claims by project and local developer. The removed bare twing align report is no longer its CLI consumer.

Small examples that make it click

A design template → file scope 
goal: Retry requests without waiting forever
plan: |
  ## Approach
  Cap exponential backoff and add a boundary test.
  ## Checks
  Verify the cap and unchanged behavior for small delays.
changes:
  - id: cap-delay
    action: modify
    target: src/net/retry.ts::RetryPolicy.backoff
    intent: Keep retry waits within the configured maximum
  - id: cap-test
    action: add
    kind: test
    target: src/net/retry.test.ts
    intent: Cover the maximum delay boundary

deriveScope(changes) returns creates: ["src/net/retry.test.ts"] and touches: ["src/net/retry.ts"]. Here “creates” means action add, not an actual filesystem-existence check.

Use core from TypeScript 
import {
  parseDesignTemplate, validateTemplate, deriveScope,
  canonicalizeRemoteUrl, computeSymbolId, pathOfTarget,
  encodeFrame, FrameDecoder, redact,
} from "@twing/core";

canonicalizeRemoteUrl("git@github.com:Team/App.git");
// "github.com/team/app"

const id = computeSymbolId("src/net/retry.ts", "RetryPolicy.backoff");
// "src/net/retry.ts::RetryPolicy.backoff"
pathOfTarget(id); // "src/net/retry.ts"

const template = parseDesignTemplate(yamlText); // caller supplies YAML string
const problems = validateTemplate(template);
if (problems.length === 0) {
  const scope = deriveScope(template.changes);
  // Caller, not core, registers template + scope with the server.
}

const decoder = new FrameDecoder();
decoder.push(encodeFrame({ type: "get_identity" }));
// [{ type: "get_identity" }]

redact("password=example-secret");
// "password=[redacted]"
Repo config is not credential storage 
# Committed: .twing/twing.yml
coordinator:
  serverUrl: https://coordinator.example.com
capture:
  enabled: true
settings:
  designDormantAfter: 7d
constraints:
  - text: Reuse the shared socket framing format
    scope: packages/core/src/framing.ts
require_human_review:
  - path: packages/server/src/identity-store.ts
    reason: Identity changes need an admin review

Personal credentials belong in ~/.twing/config.json, keyed by server URL. The example above deliberately contains no token. Rules/settings need seeding to the coordinator; merely editing the YAML is not server enforcement.

Types describe object shapes at compile time. Import them with import type; they are not runtime functions or automatic input validators. The lists below cover all exported type/interface names in the 18 source modules.

Shared domain models · types.ts
  • Edit evidence: Claim, CallEdge, Notice, FindingKind, Finding.
  • Plan declaration: DesignChangeAction, DesignChangeKind, DesignChange, DesignStatement. Actions: add, modify, rewrite, remove, rename, move. Kinds: code, api, schema, test, docs, config.
  • Checking/rules: DesignConstraintType (only constraint), DesignConstraint, DesignVerdict, DesignOverlapKind, DesignConflict, DesignCheckResult.
  • Approval workflow: PendingReview, ReviewDesignSummary, ReviewConstraintSummary, ReviewConflictSummary, EnrichedPendingReview.
  • Human review discussion: CommentAnchorField, CommentAnchor, DesignCommentStatus, DesignComment, DesignCommentReply, OpenReviewNotice.
  • Commit/dashboard reminder: DesignLink.

A design records scope/activity versions and specific approved waivers, not merely “approved forever.” Overview edits have a separate revision counter from scope changes. Optional legacy fields must not be mistaken for a fresh declaration.

Comment anchors store quotes plus surrounding text, not fragile character offsets. Comment status is open/resolved. The daemon's review notice carries comment IDs and design summary/link, never comment bodies.

What not to assume

  • Two people editing the same symbol no longer automatically triggers a conflict. Old Finding/DesignVerdict values and waiver fields remain for historical data, but current blocking conflict sources are project constraints and semantic intent divergence.
  • Core does not prove a plan was implemented correctly. Shared targets enable comparing declared vs actual work, but validateTemplate checks the declaration, not behavior or AST equivalence after rename/move.
  • Call edges are approximate and currently not used for the removed contract-break check. They are still built/uploaded; do not treat them as compiler-grade dependency analysis.
  • Only JS/TS are parsed. Other languages still yield file-level claims through the daemon, not symbol-level parsing in core.
  • Read/Grep/Glob are in the protocol but are not live soft claims. A Read may help prime future signature comparisons.
  • First observation is not proof that a signature stayed unchanged. Without a prior version the daemon has nothing to diff and can mark a first-seen symbol's signatureChanged false.
  • Shell edits/commits are not gated or claim-captured by the normal tool matchers. A commit reminder depends on the agent following it. Transcript capture can retain narrated shell findings, not raw shell output.
  • Parse helpers have different failure policies. Template parsing is tolerant; manifest/settings JSON parsing can throw; config reads fail soft. Handle each boundary deliberately.
  • TypeScript types do not validate received JSON. Framing returns unknown values, and authFetch returns a raw Response. Consumers must validate/check status themselves.
  • Redaction is best effort. Some digest/project IDs are masked intentionally; unknown secret shapes can still be missed. Capture's session-level consent is broader than a per-repo filter.
  • Some comments are historical. Source comments saying capture is local-only or unread, or describing path/symbol collision checks, can lag current call sites. This guide uses current implementations to resolve those differences.
