The big picture · no coding background required

A team of AI helpers.
One shared plan.

Twing helps people and their AI coding assistants work on the same project without silently heading in different directions.

One-sentence version: before changing code, explain your plan; afterward, leave a receipt of what you changed.

This is the high-level architecture of the project, with special attention to @twing/core. Source snapshot: 9 October 2026.

1. Imagine a school group project

You and your friends are building an app for the school library. Everyone has an AI assistant helping them write code.

Maya + her AI

“I’ll let students borrow books for two weeks.”

Leo + his AI

“I’ll make overdue reminders assuming books are due after one week.”

The code might be in completely different files. But the two plans disagree about how the app should work.

Or both AIs might build their own version of the same feature without knowing the other one is doing it.

The problem is not just “two people changed the same file.” It is “two people made plans that do not fit together.”

Twing makes plans visible, checks them against project rules and other plans, and records edits so the team has evidence of what happened.

2. Meet the five main pieces

Think of them as different jobs in your school project.

PieceSchool-project versionActual job

Hook

The monitor/dashboard is another view of the team's noticeboard: people can read designs and discuss them in a browser. Its UI is not part of the core package.

Important: core is not another worker running in the background. It is a library—a box of reusable code that the other programs use.

3. The whole system on one map

On your computer

YOU → CLI → setup and plan commands

YOUR AI → HOOK

├ Before editing → SERVER → allow or deny

└ After editing → DAEMON → SERVER → record the edit

Shared with the team

SERVER ↔ plans, rules, permissions, reviews

PEOPLE → DASHBOARD → read plans and discuss them

Underneath the TypeScript pieces

CORE → common dictionary + reusable tools

The server can be hosted elsewhere or run locally. The key idea is that participating computers talk to the same coordinator for that project.

The hook is written in Go, so it has matching copies of the wire-format and identity rules rather than directly importing the TypeScript core library.

4. Flow A: “Can I make this change?”

This is the before-edit flow. It is the checkpoint, not the note-taker.

  1. The AI describes its plan.
    “I’ll change the borrowing period and update its tests.” The plan includes why, how, and which files it expects to change.
  2. The plan gets registered with the coordinator.
    Core helps turn the written plan into a consistent format. The server stores it and checks project rules.
  3. The coordinator compares plans.
    A separate AI-powered comparison looks for duplication or disagreements in meaning. This can happen after the initial registration response.
  4. The AI tries an edit.
    The hook asks the server: “Does this session have a usable plan covering this file? Does this file need special approval?”
  5. The hook passes back the answer.
    If the checks pass, the edit can proceed. Otherwise, the agent gets a reason and the next step.

What could stop it?

  • No plan: register one.
  • File outside the plan: expand the plan or register the appropriate work.
  • A project rule needs approval: explain the exception and ask an admin.
  • Plans disagree: adopt another approach or explain why a different approach is justified.
  • The plan went inactive: explicitly resume it so checks run again.
Like a checkpoint that cannot reach its office: when a coordinator is configured but cannot be reached, the gate denies rather than guessing “yes.” A project with no coordinator configured is not gated in the first place.

Core's role: format and validate the plan. Not core's role: decide permission or run the AI comparison.

5. Flow B: “What actually changed?”

This is the after-edit flow. It is background record-keeping, not another permission request.

  1. The edit has already happened.
    The hook sends a short event to the daemon on your computer.
  2. The daemon looks at the file.
    Core's code parser helps find the function or class around the edit.
  3. It creates a receipt.
    For example: “Maya's session changed the borrowing-period function in this file at this time.” Twing calls this a claim.
  4. The receipt gets sent to the coordinator.
    The team can use the evidence to understand what was touched and compare declared work with recorded edits.

What is in the receipt?

Which project · which developer · which session · which branch · which file/function · when it happened.

It can also include old/new function signatures when the daemon has an earlier version to compare.

A signature is the function's name and input/output shape, not the whole function body.

Do not mix up the two flows: the checkpoint answers “may it happen?” The receipt says “it happened.” The receipt flow does not block the edit.

Current behavior: matching edits by two people do not automatically produce a new conflict warning. Those edit-vs-edit conflict checks were removed. The plan-meaning comparison is the current peer-conflict signal.

6. So what does core actually provide?

Imagine the CLI, daemon, and server each invented their own names and forms. One might call a project “LibraryApp,” another “library-app,” and another its folder path. They could accidentally treat the same project as three different projects.

Core prevents that kind of disagreement by supplying shared tools.

Core knows the format of a decision, not whether your particular work should be approved. It has no HTTP routes of its own and does not run a database, daemon, or AI model.

7. Optional flow C: “Keep the useful conversation”

Code receipts show what was touched. They do not explain all the reasoning that led to the change. Optional conversation capture preserves some of that context.

  1. The repo explicitly opts in.
    The committed project config must say capture is enabled. Installing the CLI does not enable it by itself.
  2. The daemon reads the existing session history.
    Different coding tools store history differently; adapters translate it into the common shape.
  3. Core filters and cleans it.
    Keep human messages, assistant explanations, and selected file paths. Drop raw tool inputs/results, thinking blocks, and injected noise. Mask likely credentials in retained text.
  4. The daemon saves and uploads new records.
    Progress markers let it continue from where it left off. It does not need to wait until the conversation ends.

The server can use captured context internally for features such as private questions about a design. There is no public “download raw captures” API in this code path.

Privacy detail worth understanding: consent is sticky for the conversation. After an opted-in repo qualifies the session, later captured discussion can include other repos too. Secret masking is best effort, not a promise that every secret will be caught.

Core's role: cleanup rules. Daemon's role: consent boundary, reading, progress, storage, and upload. Server's role: receiving records and using permitted context.

8. One complete story

Let's return to Maya and Leo's library app.

  1. Maya sets up the repo. The CLI connects her checkout to the team's coordinator and prepares the local hook/daemon.
  2. Maya's AI registers a plan: “Students can borrow books for two weeks.”
  3. Leo's AI registers a plan: “Send overdue reminders after one week.”
  4. The server's semantic comparison may spot the mismatch. It can flag both plans and open an alignment discussion. This is an AI judgement, not an infallible guarantee.
  5. They reconcile their approaches. They adjust their plans, adopt the appropriate design, or justify a difference through the resolution workflow. Simply closing a discussion thread is not the same as clearing a design block.
  6. Before each covered edit, the hook checks permission. The active plan must cover the file, with no unresolved applicable rule block.
  7. After edits, the daemon sends receipts. Core helps label the functions that were changed.
  8. People review the work in the dashboard. A design link can be put in the commit message so future readers can find the reasoning.

The payoff is not “AI can never make a mistake.” It is “the team has visible plans, explicit disagreements, and records of what happened.”

9. What this system does not magically do

  • It does not replace git. Git still handles commits, branches, and merging.
  • It does not prove code is correct. A well-filled plan and an edit receipt are not substitutes for tests or review.
  • It does not understand every programming language at function level. Core's parser currently supports JavaScript/TypeScript. Other files can be recorded at file level.
  • It does not catch every way of editing a file. Normal shell-driven edits are not covered by the edit-tool gate/claim matchers.
  • It does not put every decision in core. Approval, memberships, plan lifecycle, and semantic conflict checks belong to the server/hook layers.
  • It does not automatically write commit links. It reminds the agent; the agent has to add the trailer.
Why separate the checkpoint and the note-taker?

Permission needs an answer right now, before the edit. So the hook asks the coordinator directly.

Detailed record-keeping can happen afterward. So the hook quickly passes that work to the daemon and avoids putting parsing/upload work in the edit's way.

Different jobs, different timing. Sharing core tools keeps their vocabulary consistent without making them the same flow.
